# The framework is a portable kernel with harness adapters

The framework has to run inside agent harnesses that disagree about almost everything: how agents are defined, how subagents are dispatched, which tools exist, how hooks fire, and how instructions are loaded. Pi ships packages, skills, and extensions but not built-in subagents; Claude Code ships persistent agents and hooks but is model-bound; other harnesses offer some subset. If the framework's definition lives in any one harness's configuration format, it becomes a different framework per harness, and the vocabulary drifts with it.

We therefore separate the **specification** from the **runtime**. `.garden/` is the canonical, harness-neutral source of truth: packets, agent roles, stakes, journal, leases, and gate policy, all in plain Markdown, YAML, JSONL, and TOML. A `garden` kernel owns the semantics that must not diverge — packet resolution and semver compatibility, journal and lease validation, gate evaluation, and ripeness orchestration. Harness adapters are thin translations from kernel events to native primitives, and from canonical files to generated harness artifacts.

The kernel is opinionated. Portability is not achieved by reducing the framework to the lowest common denominator; it is achieved by keeping the semantics in one place and letting adapters declare which of them they can enforce. A harness that cannot enforce a gate does not get a weaker definition of the gate; it gets a warning that the gate is advisory there.

**Consequences:** `.garden/` is the only artifact a gardener edits by hand. Generated `.pi/` and `.claude/` artifacts are build outputs, committed for reproducibility and checked with `garden sync --check` in CI. Adapters may not invent semantics; they translate. A new harness is supported by writing an adapter, not by forking the framework. The kernel must be usable headlessly, because every adapter calls it the same way. The kernel's language and distribution are implementation decisions, not framework decisions.

**Considered options:** one harness's native config as the definition (rejected: lock-in, and the vocabulary becomes harness-specific); prompt-only portability with no kernel (rejected: no shared semantics, no enforcement, and every adapter reimplements gates); an MCP server as the only integration surface (rejected: MCP tools are model-invoked, so gates become suggestions); a general agent framework such as LangGraph or CrewAI as the runtime (rejected: it is a separate product, not something installed into a repository); separate frameworks per harness (rejected: guaranteed drift, and the seed bank stops being one lineage).
